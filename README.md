# Nictiz tooling for IGs
This repo contains the custom tools used by Nictiz for working with FHIR IG's.

These tools are all Node scripts, for the simple reason that Sushi is also a Node script, so the assumption is that Node is installed and working when building an IG.

# Installation
The tools in this repo are installed together on your computer. To do so:

    npm install -g github:Nictiz/Nictiz-tooling-for-IGs

The tools listed below can than be used as command line tools.

Alternatively, the tools can be installed locally for an IG repository, e.g. if the tools make a breaking change in the behavior:

    npm install github:Nictiz/Nictiz-tooling-for-IGs

This will put a folder called `node_modules` in your repo. Make sure to put it in your `.gitignore` file. Scripts can be run from this folder using:

    npm exec -- [script name] [arguments]

# Tools
## excel-to-artifacts
This is the most important script, as this is really the glue between the Excel based method to collect and document requirements and model choices within Nictiz, the ART-DECOR based method to define logical models and terminology artfiacts, and publications using a FHIR IG. More specifically, it does te following:

1. Convert the Concept tab in Excel to a Markdown file.
2. Convert the information requirements to a Requirements resource.
3. Download the logical model as noted on the Concept tab of the Excel as FHIR logical model.
4. Download linked ValueSets from the logical model or from FHIR-resources from ART-DECOR.
5. Download ActorDefinitions from ART-DECOR.

By default, the script does all these things. There are command line flags to perform specific actions.

The script requires two input arguments and one setting:

1. The `inputFolder` argument: the parent folder for the Excel files and FHIR profiles; the Excel files should be in a sub folder called "requirements" and the profiles in a sub folder called "profiles".
2. The `outputFolder` argument: the parent folder in which all output should be placed. This folder should be excluded from git.
3. The setting "ad-project" in the section "nictizIgConfig" of `sushi-config.yaml`. This should be the prefix of the ART-DECOR project this IG is linked to.

## translate-menu
This is really a workaround for the way menu's are defined in FHIR IG's. The IG Publisher requires a verbatim XML fragment to included, which is not really human-maintainable. Sushi puts a wrapper in from of this, allowing you to define the menu structure in `sushi-config.yaml`. However, Sushi doesn't offer a translation mechanism, which is where this script comes in. It reads the menu entries from `sushi-config.yaml`, then loads translations from the `menu.po` translation file in the `input/translations/[language]` folder, then takes the `menu.xml` generated by Sushi, and generates a translated version. Finally, it will write out `menu.po` again with all translated and untranslated menu entries, to further work on the translation.

WARNING: this whole method interferes with Sushi if you're not careful. _If_ a `menu.xml` is present in the input folder, Sushi won't overwrite it. But if `menu.xml` is _not_ present in the input folder, the IG Publisher doesn't pick up translations. So in order for this to work, you need to take care of the following:

1. Make sure that in the calling script, remove `menu.xml` from the before running Sushi input folder.
2. Make sure `menu.xml` and its translations are in `.gitignore`, so as not to accidentally commit them.
2. Run this script after calling Sushi to provide the translation.

For details about running the script, run `translate-menu --help`.

## sync-obligations
This script is used to match the obligations defined in the logical model against those defined in the FHIR profiles. This is based on the mapping elements in the profiles, which are used to relate profile elements to elements in the logical model.

The script can either be used to check if the obligations align, or to actually copy over the obligations in the profiles. The check mode can be used as an automated QA process. There could be good reasons for obligations to not align exactly, e.g. when there is an inexact match between the model and FHIR a deliberate exception can be made. For this reasons, known exceptions can be documented in the known-issues.yaml file. For the same reason, it is discouraged to use the copy mode of the script as part of an automated process. If there are deliberate mismatches, you don't want to overwrite them; setting of changing obligations should be a concious process.

For details, run `sync-obligations --help`.
